# Phase 2 — UI Design Contract: Mascot Module

> Visual and interaction contract for the reusable, feature-agnostic raccoon-mascot module (MASC-01..04). Generated by gsd-ui-researcher, verified by gsd-ui-checker. This is a **component contract**, not a screen contract — it constrains `<Mascot />`, the module every later phase mounts into a host screen.

**Locked upstream inputs used (not re-asked):** `design/DESIGN-SYSTEM.md` (palette, dual-accent observation, per-screen mascot appearances, constraint watch-items), `theme/tokens.ts` (landed dark tokens), `.planning/REQUIREMENTS.md` MASC-01..04, `.planning/ROADMAP.md` Phase 2 success criteria, `CLAUDE.md` PDA-aware/shame-free hard constraints, existing `src/components/MascotSlot.tsx` (Phase 1 integration seam this module replaces).

## Mascot Module Contract

*(Extends the base template — a reusable animation module needs a state/API contract beyond copy and color.)*

### State → slot mapping (MASC-01)

Slot names are final-art-compatible: placeholder and final Lottie JSON files both use `assets/mascot/mascot_<state>.json`, exactly matching the five requirement state names below. The artist drops in final art with **zero code changes** as long as filenames and marker names (see Idle micro-behaviors) are preserved.

| State (slot key) | Asset filename | Trigger — what makes the HOST set this state | Playback | Auto-returns to |
|---|---|---|---|---|
| `greeting` | `mascot_greeting.json` | Host sets it once when the mascot module is first shown in a fresh app-open/session context (e.g. cold launch reaching Home). This is a **reaction to the user opening the app**, not the mascot initiating anything — see FLAG 3 for cadence policy. | one-shot | `idle` (module calls `onStateAnimationComplete('greeting')`, host or module internally advances to `idle`) |
| `idle` | `mascot_idle.json` | Default/resting state whenever no more specific state applies (Home hub baseline, Settings screen, any screen with no active flow) | continuous loop + micro-behavior segments | stays `idle` |
| `presence` | `mascot_presence.json` | Host sets during an active Co-pilot session ("I'm here with you, doing my thing" — wired in Phase 3) | continuous loop | stays `presence` until host changes it |
| `dozing` | `mascot_dozing.json` | Host sets after ~30 minutes of session time (Phase 3, PILOT-04) — the mascot reacts to the session's elapsed time, it does not track its own clock | continuous loop | `presence` on host-detected touch/session-end (host decision, not module's) |
| `acknowledge` | `mascot_acknowledge.json` | Host sets on a discrete, already-completed user action: brain-dump capture turn ends, session ends, an item/Starter is saved. Never acknowledges something the user hasn't done yet. | one-shot | previous state or `idle` (module calls `onStateAnimationComplete('acknowledge')`) |

**MASC-03 hard constraint restated as a build rule:** there is no sixth state, and no code path may construct a "sad", "disappointed", "waiting", or "nagging" animation. If a future phase is tempted to add one, that is a bug against this contract, not a missing feature.

### Idle micro-behaviors (MASC-02)

Three named segments authored as markers **within `mascot_idle.json`** (not separate files — this keeps MASC-04's single-persistent-`LottieView` contract intact by playing frame-range segments on the one mounted view instead of swapping sources):

| Micro-behavior | Marker name | Approx. clip length | Selection weight |
|---|---|---|---|
| Blink | `blink` | 0.3–0.5s | 50% |
| Glance | `glance` | 0.8–1.2s | 30% |
| Posture shift | `postureShift` | 1–2s | 20% |

**Randomized-interval contract:**
- While `state === 'idle'`, schedule the next micro-behavior at a random interval **uniformly between 4,000ms and 9,000ms** (normal) — this is bounded, calm, and non-attention-grabbing by design (never sub-second, never a fixed cadence a user could subconsciously anticipate as "waiting for something").
- Under reduced-stimulus (see below), widen the interval to **12,000–24,000ms**.
- At each trigger, weighted-randomly pick one of the three markers, play only that frame range via the LottieView segment-play API, then resume the base idle loop and re-schedule.
- Micro-behaviors never overlap each other and never fire during a `greeting`/`acknowledge` one-shot (the scheduler pauses while a one-shot state is active and resumes once the module returns to `idle`).

### Presence prominence levels (Settings-driven public prop)

The Settings mockup (`design/mockups/fae1f5f8-Settings___profile.html`) shows a "Mascot · Presence · Prominent" row, confirming a user-facing prominence scale exists but only shows the currently-selected value. This UI-SPEC defines the full scale:

| Level | Size preset | Opacity | Micro-behavior frequency | When a user picks this |
|---|---|---|---|---|
| `prominent` (**default**) | `lg` (220×220) | 1.0 | normal (4–9s) | Default for every new install — matches the mockup's shown value |
| `subtle` | `md` (140×140) | 0.85 | normal | User wants a quieter visual footprint without turning presence off entirely |
| `hidden` | none — module renders nothing, height 0 | 0 | n/a (scheduler paused) | User wants the mascot gone from view; the module still tracks its logical `state` internally so re-enabling prominence resumes seamlessly with no re-greeting |

The module does **not** read this setting itself — it stays feature-agnostic and testable in isolation. The host (eventually the Settings screen, Phase 8) reads `mascotProminence` from the `settings` MMKV repo and passes it down as the `prominence` prop. See FLAG 2 for the storage recommendation.

### Public component API

```ts
type MascotState = 'greeting' | 'idle' | 'presence' | 'dozing' | 'acknowledge';
type MascotProminence = 'prominent' | 'subtle' | 'hidden';
type MascotSize = 'lg' | 'md' | 'sm'; // lg=220, md=140, sm=64 — optional explicit override

type MascotProps = {
  state?: MascotState;                 // default 'idle'
  prominence?: MascotProminence;       // default 'prominent'
  size?: MascotSize;                   // optional; else derived from prominence (prominent→lg, subtle→md)
  reducedStimulus?: boolean;           // default: OS AccessibilityInfo.isReduceMotionEnabled(); host may OR in the in-app Settings toggle
  accessibilityLabel: string;          // required — host-translated, per current state (see Copywriting Contract)
  onStateAnimationComplete?: (state: MascotState) => void; // fires once a one-shot (greeting/acknowledge) finishes playing
  testID?: string;
};
```

Deliberately **no `style` prop** — this keeps the visual contract locked to the token-driven size presets above; a host wraps the module in its own layout container (`View` with `theme.spacing.*` padding/gap) rather than reaching into the mascot's own dimensions. This preserves "feature-agnostic, reusable across any screen" (Phase 2 goal) without letting each screen silently reinvent the mascot's size.

### Transition contract

- One-shot states (`greeting`, `acknowledge`) auto-complete and call `onStateAnimationComplete`, letting the host chain further UI (e.g., a session-end flow that waits for the warm acknowledgment before navigating away — PILOT-05 territory in Phase 3).
- State swaps update the single persistent `LottieView`'s `source`; wrap the visual swap in a **120ms opacity fade** (Reanimated) on the view's container — a lightweight fade, not a second mounted Lottie instance, so MASC-04's "single persistent LottieView" requirement holds at all times, including mid-transition.
- Under reduced-stimulus, extend the fade to 200ms (calmer, not faster) rather than removing it — motion can't be fully eliminated from a Lottie-based module, only slowed and spaced out.
- Do not implement a two-instance crossfade — unnecessary GPU/JS-thread cost on the low/mid-tier Android target this phase must verify against (MASC-04, roadmap success criterion 4).

### Asset & performance contract (MASC-04)

- Exactly **one** `<LottieView>` mounted per module instance, always — never two overlapping instances, including during transitions.
- Each of the 5 state JSON assets is loaded lazily (dynamic `require()`/import at the point a state first becomes active), not all bundled/decoded eagerly at module mount.
- Once loaded, cache the resolved source per state for the module instance's lifetime so re-entering a state doesn't re-decode JSON.
- Every Lottie asset (placeholder now, final art later) must stay **under 300KB** — the Phase 2 plan should include a size-check script (mirroring `scripts/check-hex-literals.mjs`'s fail-closed pattern) that fails the build if any `assets/mascot/*.json` exceeds 300KB.
- Placeholder assets this phase: simple geometric/shape-based placeholder loops (not final raccoon art — that's pending from the founder per `.planning/STATE.md`), authored with the exact 5 filenames and 3 marker names above so final art is a pure drop-in replacement.

### Reduced-stimulus / accessibility contract

- On mount, subscribe to `AccessibilityInfo.isReduceMotionEnabled()` + its change event (OS-level reduce-motion).
- Combine (logical OR) with the explicit `reducedStimulus` prop the host passes down from the in-app Settings "Reduced stimulus" toggle (`design/mockups/fae1f5f8-Settings___profile.html` shows this as "Always dark" today under Comfort — the mascot module should honor the same reduced-stimulus signal, not invent a separate one).
- Effect when active: idle micro-behavior interval widens to 12–24s (see above); transition fade extends to 200ms. `presence`/`dozing` loops are already calm ambient loops and are unaffected — only idle cadence and transition timing respond.

## Flags (non-blocking — recommended defaults, confirm only if founder has a strong opinion)

1. **Custom font loading (Fraunces/Inter/JetBrains Mono) — RECOMMEND DEFERRING out of Phase 2.** This module renders no text; `theme.typography.fontFamily: 'System'` stays as-is. Do not add `expo-font` asset loading as a Phase 2 task. The more natural first candidate is whichever phase first needs display-quality headings (Phase 6 Onboarding's "Hi. I'm glad you're here." is the leading candidate) — flag it there instead.
2. **Prominence persistence.** Recommend adding `mascotProminence: 'prominent' | 'subtle' | 'hidden'` (default `'prominent'`) to the existing Phase 1 `settings` MMKV repo now, even though the Settings *screen* UI to change it doesn't land until Phase 8. This gives the module a real field to read via host-provided prop from day one instead of a hardcoded literal.
3. **Greeting re-trigger policy is a host decision, not a module decision.** Recommend the host decide cadence using an in-memory flag scoped to the app session (e.g., "greet once per cold launch"), never a persisted "last greeted at" timestamp — persisting that would edge toward a disguised daily-aggregate field, which the schema denylist test (Phase 1) is built to catch. The module itself has no opinion; it renders whatever `state` it's given for as long as it's given.
4. **`colors.mascotGlowDeep` (`#E8B05C`) — deferred, not added this phase.** Add only if the placeholder or final `presence`-state art gives a concrete reason for two distinct glow intensities. Don't pre-add an unused token.
